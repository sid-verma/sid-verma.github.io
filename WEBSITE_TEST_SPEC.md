# Component and animation verification specification

Status: specification approved for use during implementation; tests below have not yet been executed. This document defines required observations, not claims of passing results.

## Test environment and evidence

- Capture the current rendered baseline before application edits. Record commit, uncommitted source state, build command, browser/version, viewport, device pixel ratio, theme, and motion preference. Build the final source again before final verification.
- Use actual generated pages: homepage, archive, tags, sequence index/detail, about, 404, and articles covering long titles, nested lists, blockquotes, tables, code, diagrams, and contents navigation. Record exact URLs in the results. If an edge case is absent, use a temporary test fixture outside published content.
- Layout matrix: widths 360, 390, 768, 1024, 1280, and 1440px; use fixed documented heights. Check every route type at 390 and 1440px; homepage and representative complex article at every width. Test both themes on desktop and mobile. Check breakpoint boundaries at one pixel below, at, and above each modified breakpoint.
- Test normal motion and reduced motion, keyboard and pointer navigation, touch-sized targets, and 200% zoom. Check reflow at a 320 CSS-pixel viewport. Use Chromium and, when available, Firefox and WebKit; unavailable engines are explicitly untested, not assumed compatible.
- Separate automated assertions from visual and assistive-technology review. Prefer semantic locators and observable behavior; do not pass a test solely because the expected class exists. Use condition-based waits, not arbitrary sleeps, except controlled animation sampling.
- Save before/after screenshots with matching dimensions and stable font/image readiness. Mask only changing content such as dates when necessary; never mask the component being tested. Inspect differences, not only pixel counts. No global pixel threshold can approve intentional redesign and detect all regressions.
- Each test result records ID, route, environment, steps, expected/actual outcome, evidence path, and PASS / FAIL / BLOCKED / NOT RUN. Any fix requires rerunning its failed case and affected adjacent cases.

## Animation-specific contract

Before coding each effect, record its trigger, animated properties, start/end values, duration, easing, interruption behavior, and reduced-motion result. Initial design ranges are 120–180ms for feedback and 180–220ms for drawer/search entry or exit; finalize exact token values before testing. These are design choices, not verified LessWrong timings.

| ID | Trigger and measurements | Pass criteria |
|---|---|---|
| MOTION-01 | Hover and keyboard-focus header actions, navigation links, feed controls, and artwork. Sample computed/visible start, intermediate, and settled states. | Only specified properties change; feedback is visible and ends at the correct state. No text reflow, neighboring displacement, flicker, or hover-only access to essential controls. Keyboard focus remains distinct from hover. |
| MOTION-02 | Open/close drawer and search. Capture start, an intermediate sample, and completion; inspect animation events or equivalent browser animation timeline. | Intermediate state demonstrates actual motion/fade, not merely a matching duration declaration. Final state completes within configured duration + 100ms under controlled idle test conditions. CSS duration/easing agree with the contract. Hidden state removes hit targets and focus access at the specified point. |
| MOTION-03 | Reverse open/close rapidly, activate twice, dismiss while opening, and resize during movement. | Last user intent wins; no stuck intermediate transform/opacity, duplicate handlers, focus loss, stale backdrop, or scroll lock. Final state settles within the final transition duration + 100ms. |
| MOTION-04 | Scroll/select collections and use deep links with normal and reduced motion. | Normal movement reaches the intended visible target without moving unrelated page regions unexpectedly. Reduced motion performs immediate movement and disables decorative transforms. Verify actual scroll/frame behavior, not only media-query presence. |
| MOTION-05 | Toggle theme during hover and with an overlay open. Check mid-transition text/surface contrast and settling. | No unreadable intermediate combination, flash of the wrong theme, or layout movement. Reduced motion removes the theme transition. |
| MOTION-06 | Enable reduced motion before load, then change preference during the session when supported. Exercise every animation above. | State changes remain functional; spatial effects, continuous animations, and forced smooth scrolling are absent. Preference changes apply without reloading where supported by implementation. |
| MOTION-07 | Record a browser performance trace during drawer, search, and artwork transitions on a representative desktop and mobile-sized viewport. | Prefer compositor-friendly opacity/transform for spatial effects. No animation-attributable long task over 50ms in a controlled run. Report observed dropped frames/stutters and device conditions; do not claim universal 60fps from one trace. |

Do not use wall-clock timing assertions under arbitrary CI load to prove visual quality. Repeat a timing failure in a controlled run, preserve the trace, and distinguish scheduling noise from implementation failure. Search and filtering tests should await meaningful state; animation tests additionally measure intermediate rendering.

## Reference fidelity and release gate

Compare local and LessWrong captures at matching viewport sizes for hierarchy, usable reading width, density, typography roles, artwork treatment, and interaction feedback. Record exact reference URL and capture date. Inspect reference interactions before claiming equivalent behavior or timing. Pixel similarity across different content is not a correctness test.

Agents submit test IDs, evidence, and remaining limitations with their changes. Primary agent verifies integrated behavior, especially drawer/search interaction, shared theme tokens, feed markup/handlers, and responsive boundaries. All P1 behavior and touched component cases must pass; failures block completion. BLOCKED/NOT RUN tests remain explicit gaps and cannot be reported as passes. No “fully verified” claim is permitted while required browser, animation, or accessibility checks remain unexecuted.
